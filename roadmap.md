## Этап 3: единый метод запросов + проработка озвучки манги (сделано 2026-09-26)

За образец взят метод отправки сообщения (`useChat.sendMessage`): UI обновляется до ответа,
запрос уходит с `signal`, отмена не считается ошибкой, причина отказа от сервера доезжает
до пользователя, результат раскладывается по элементам одним апдейтом состояния.

- [x] **Общий слой запросов к edge-функциям** (`src/lib/edgeAuth.ts`): `edgeRequest` /
  `edgeJson` / `edgeBlob` — те же заголовки `Authorization: Bearer <access_token>` + `apikey`,
  обязательный `AbortSignal`, одна обработка ошибок (`{ error }` → текст → `Ошибка <код>`) в
  `EdgeRequestError`; `isAbortError` отличает «Стоп» от сбоя
- [x] **Отправка сообщения переведена на этот слой**: `sendMessage` и автораскладка
  `[IMAGE_SEARCH: …]` больше не собирают fetch руками, а в toast при сбое потока попадает
  текст сервера вместо общей формулировки
- [x] **Озвучка манги вынесена в метод-хук** `src/hooks/useMangaVoice.ts` (по образцу `useChat`):
  - анализ всей очереди страниц одним нажатием — батчи по 5 уходят последовательно,
    виден прогресс («Батч 2 из 3 · обработано 5 из 12»);
    упавший батч не отменяет уже разобранные страницы и возвращается в очередь;
  - `stop()` рвёт текущий запрос и всю очередь озвучки (в модалке появились кнопки «Стоп» —
    общая и по кадру), отмена не показывается ошибкой;
  - «Озвучить всё» не останавливается на первой неудаче: страницы, которые не удалось озвучить,
    помечаются причиной прямо на кадре, остальные продолжают очередь;
  - ошибки запросов показываются и в плашке, и в toast — окно может быть закрыто в момент ответа;
  - состояние переживает закрытие окна: страницы и готовая озвучка не теряются,
    но при повторном открытии не стартуют сами;
  - страницы/голоса читаются из ref, который синхронизируется в момент апдейта, поэтому
    «поправить реплики → сразу озвучить всё» не работает по устаревшему снимку
- [x] Серверные функции не менялись: контракт `manga-analyze` и `dialog-tts` прежний
- [x] Дев-стенд `#manga-preview` (`src/components/dev/MangaVoiceDemo.tsx`): окно озвучки
  с имитацией edge-функций, сценариями «медленный ответ / ошибка / запрос висит»
  и журналом запросов (виден `signal` каждого вызова). В production-сборку не попадает
- [x] Тесты: `useMangaVoice.test.tsx` (25 — заголовки, signal, батчи, отмена, ошибки,
  очередь озвучки, уборка object URL, стражи «метод тот же, что в чате»),

### 3.1 Настройка самого запроса — против «Failed to fetch» (2026-09-26)

`TypeError: Failed to fetch` — ошибка без причины: так выглядят и обрыв сети, и блокировка CORS,
и незадеплоенная функция, и закрытый исходящий доступ (в песочнице предпросмотра Arena соединения
к `*.supabase.co` обрываются до TLS — проверено). Поэтому запрос настроен так, чтобы доходить
и всегда объяснять, что случилось:

- [x] **Dev-прокси для edge-функций** (`vite.config.ts`): в dev клиент ходит на свой origin
  `/functions/v1/...`, а Vite проксирует на Supabase. CORS, блокировщики и ограничения чужих
  песочниц на запрос больше не влияют; в сборке остаётся абсолютный адрес проекта
- [x] **Таймаут на установку ответа** (140 с — больше серверных 120 с у `manga-analyze`):
  без него `fetch` висит, пока соединение не оборвёт прокси. Таймер снимается после заголовков,
  а связь с внешним `AbortSignal` живёт до конца тела — иначе «Стоп» во время чтения SSE-стрима
  не отменял бы запрос (найденный баг)
- [x] **Один повтор** на сетевой сбой и таймаут (прикладные 4xx/5xx не повторяются),
  отмена пользователем не повторяется и не показывается как ошибка
- [x] **Внятные тексты вместо «Failed to fetch»**: `NETWORK_ERROR_MESSAGE` и
  `TIMEOUT_ERROR_MESSAGE` в `EdgeRequestError` (+ флаги `network` / `timedOut` и лог с URL)
- [x] **Тело `manga-analyze` больше не раздувается**: страницы готовятся заранее
  (`prepareAnalyzePayload`), батчи режутся по фактическому размеру payload
  (`planAnalyzeBatches`, бюджет 6 МБ при серверном лимите 5 картинок), а страницы, из-за которых
  батч не влезает, пережимаются жёстче (1280 px / 700 КБ). В модалке на это время —
  «Готовлю страницы к отправке…» и прогресс «Батч 2 из 3 · обработано 5 из 12»
- [x] Дев-стенд `#manga-preview` объясняет, почему настоящие функции в песочнице недоступны,
  и ловит любые вызовы `functions/v1/*`
- [x] Тесты: `edgeRequest.test.ts` (16 — заголовки, signal, таймаут, повтор, отмена),
  `requestConfig.test.ts` (11 стражей настройки), дополнения `mangaPages.test.ts` (10) и
  `useMangaVoice.test.tsx` (27) — всего 291 тест

### 3.2 Точная причина сбоя, строгий промпт анализа и процесс с анимациями (2026-09-27)

- [x] **Точная причина вместо «Failed to fetch»**: сообщение собирается как
      `Ошибка запроса api (<этап>: <причина>)`, где этап — конкретный шаг конвейера
      (`src/lib/mangaRequestError.ts`): добавление страницы → чтение файла → сжатие изображения →
      отправка запроса → ответ api анализа → обработка ответа → проверка реплик → ответ api озвучки →
      обработка аудио. Сетевой сбой всегда называется «отправкой запроса» (до сервера дело не дошло),
      прикладная ошибка — этапом api, непригодные реплики — «проверкой реплик». Рядом выводится
      HTTP-код, та же строка уходит в toast и в `voiceError` конкретной страницы
- [x] **System prompt `manga-analyze` переписан под строгий формат**: `transcript` — только строки
      `Speaker 1: …` с конкретными номерами 1–8 (никаких «Speaker N»), между репликами пустая строка,
      номера персонажа стабильны между страницами, персонаж без слов — `Speaker N: (без слов)`,
      ноль лишнего текста; описание сцены остаётся в JSON-поле `description` (держит номера
      персонажей), но в диалоге не показывается. **Нужен деплой функции**
      (`supabase functions deploy manga-analyze`)
- [x] **Клиентская страховка** (`dialogueOnly` + `formatTranscript` в `src/lib/mangaTranscript.ts`):
      даже если модель игнорирует промпт, из ответа вырезаются заборы кода, «Описание: …»,
      «Примечание: …», «[Кадр 1]», markdown и чужие имена при явных `Speaker N`, а реплики
      форматируются ровно как в примере
- [x] **Процесс видно** (`src/components/MangaProgress.tsx` + стили в `src/index.css`): кольцо-прогресс
      с процентами, орбита из иконок этапов, мерцание, бейдж «ЭТАП 3 / 5», подписи вида
      «Батч 2 из 3 · обработано 5 из 12 страниц»; проценты считаются от фактической работы
      (сжатие 10%, анализ по батчам, озвучка по страницам очереди)
- [x] **Раскладка кадра**: реплики по ролям (`Speaker 1` + имя персонажа + текст) → плеер с озвучкой →
      страница поверх них; пока кадр не озвучен, изображение остаётся превью сверху. Правка реплик —
      кнопкой «Править реплики» (textarea скрыт, но остаётся в DOM)
- [x] Тесты: этапы и точные причины в `useMangaVoice.test.tsx` (30), стражи промпта в
      `mangaAnalyze.test.ts` (23, +4), `dialogueOnly`/`formatTranscript` в `mangaTranscript.test.ts` (25, +10),
      UI-проверки диалога, кольца-прогресса и слоя страницы в `mangaVoiceModal.test.tsx` (27) — всего 312

### 3.3 Смена api в анализаторе манги (2026-09-27)

Раньше `manga-analyze` был зашит на одну модель (`google/gemini-3-flash-preview`), а переключатель
моделей чата на анализ не влиял. Теперь api выбирается в самом окне манги и доезжает до сервера.

- [x] **Переключатель в шапке окна** (`src/components/MangaApiSelector.tsx`): компактный аналог
      `ModelSelector` — те же имена (`HikkoGPT`, `HikkoGPT Smart`, `HikkoGPT Turbo`, `Спорящий`),
      но без персонажей чата: для разбора страниц они смысла не имеют. Панель позиционируется `fixed`
      от кнопки, поэтому не обрезается краями диалога; закрывается по Escape и клику мимо.
      Во время запроса переключатель заблокирован — батч должен пройти на одной модели
- [x] **Общий список и хранение выбора** (`src/lib/mangaApi.ts`): имена, подписи, `DEFAULT_MANGA_API`,
      `loadMangaApi`/`saveMangaApi`/`hasStoredMangaApi` с защитой от недоступного localStorage
      (приватный режим) и от мусора в хранилище. Выбор окна манги хранится отдельно от чата, но пока
      своего выбора нет — берётся модель чата (`chatModel` → `preferredApi`), поэтому
      `Index.tsx` → `ChatInput` → `MangaVoiceModal` прокидывают `selectedModel`
- [x] **Хук** (`src/hooks/useMangaVoice.ts`): `apiModel` + `setApiModel` (имя не из списка на сервер
      не уходит), модель берётся один раз на запуск (`apiModelRef`) и кладётся в тело каждого батча —
      `{ images, model }`; смена api посреди главы не смешивает нумерацию персонажей между батчами.
      Имя api видно в процессе: `analyzeProgress.model` и строка «Api анализа: …» под кольцом
- [x] **Сервер** (`supabase/functions/manga-analyze/`): `MANGA_MODEL_MAP` + `toAiModel` в `parse.ts`
      мапят имя в модель шлюза (неизвестное имя или старый клиент без `model` → модель по умолчанию,
      запрос не ломается); системный промпт вынесен в `SYSTEM_PROMPT` и используется обоими api,
      поэтому формат реплик от выбора api не зависит. **Нужен деплой функции**
- [x] **Запасной api**: при 402/429/5xx основного (`shouldSwitchApi`) функция пробует прямой Google
      Gemini по ключам `GEMINI_API_KEYS` (`tryGeminiAnalyze`, тот же маппинг `toGoogleModel`, что в
      `chat`). Страницы переводятся из `image_url` в `inline_data` (`dataUrlToInlineData` +
      `geminiAnalyzeBody`), иначе запасной api не увидел бы картинок; ответ разбирается тем же
      `extractJson`/`normalizePages`. Если ключей нет или все ответили ошибкой — пользователь получает
      прежнюю понятную причину основного api
- [x] Тесты: `mangaApi.test.tsx` (18 — совпадение списков клиента и сервера, хранение выбора,
      поведение переключателя, стражи), `mangaAnalyze.test.ts` (+10 на `toAiModel`, `toGoogleModel`,
      `shouldSwitchApi`, `geminiAnalyzeBody`, `geminiText`), `useMangaVoice.test.tsx` (+9: `model` в
      теле, память выбора, приоритет своего выбора над моделью чата, один api на весь запуск),

      все батчи на одном api) — всего 356

### 3.4 Причина сбоя dev-прокси вместо пустого «Ошибка 500» (2026-09-27)

В песочницах/превью выхода к `*.supabase.co` нет: прокси Vite падал на TLS-рукопожатии
и отдавал браузеру пустой `500 text/plain`. Клиенту нечего было показать, кроме кода —
`Ошибка запроса api (ответ api анализа манги: Ошибка 500)`, хотя запрос до функции не доходил
и виноват не api.

- [x] `vite.config.ts`: обработчик `proxy.on("error")` отвечает `502` с телом `{ error }` —
      «Dev-прокси не достучался до Supabase: <причина>. Запрос к функции не уходил…».
      `edgeAuth` разбирает его как любой ответ сервера, поэтому причина доезжает до плашки,
      toast и `voiceError` страницы. Заголовки не перезаписываются, если ответ уже начат
- [x] Ключи api в этом не участвуют: `LOVABLE_API_KEY` (основной api) и `GEMINI_API_KEYS`
      (запасной) живут только в секретах Supabase — в клиентский `.env` и в репозиторий не попадают
- [x] Тест-страж в `requestConfig.test.ts` (+1, всего 357)
